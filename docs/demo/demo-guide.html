软件怎么算账(架构与计量语义)

类比:一栋楼一个总电表、住 8 户。Aitra Meter 给每户装分表、每 30 秒抄一次、给每户开账单——"户"是模型,"单价"是 J/token(每生成一个字花多少焦耳)。核心规则:电按卡计,卡按持有 pod 分组,求和只在组内。

2.1 每 30 秒一轮的"抄表"(采集器)

  1. 查住户名单 — 读 kubelet 的 device-plugin checkpoint,得到"哪个 pod 占哪几张卡"(K8s 本来就记着,零配置;新模型上线自动入册、下线自动销户);
  2. 抄电表 — 从 dcgm-exporter 读每张卡的累计能耗计数器,本次减上次 = 这 30 秒该卡的耗电;
  3. 数产量 — 逐个 pod 抓它自己的 vLLM /metrics,token 计数器同样两次相减;
  4. 记账 — 每模型一条报告(能耗 = 恰好它持有的卡;TP 多卡自动求和),外加一条"无人持有的卡"的残余报告。8 模型即每窗口 9 条。

2.2 算账器的四条显示语义(最近两天新增的都在这)

情形J/token 显示理由
正常服务窗口(≥30 token)实测值分子分母都有统计意义
窗口 token 不足 30(断流边界、深度排队)0几个 token 除出来的单价是噪声——热 GPU ÷ 极小分母会得到荒谬大的假数字,一律不展示
模型占卡但零流量(空载)0(功率照实显示)看板必须反映"现在",不冻结旧值;占卡的静息电费在功率面板如实可见
无人持有的卡不进任何模型账单单独记为 idle 残余,是"真待机"

一句话口径:看板上的 J/token 要么是可信测量,要么是 0,没有中间态。配套的 CV 门(变异系数 <3% 才算稳定)在旁边面板持续背书。

2.3 J/token 怎么验算(现场可复现)

时间约掉后 J/token ≈ 功率 ÷ 吞吐。实测例(0.8B 高并发时):199.3 W ÷ 2294 tok/s = 0.087 J/token,与看板 0.09 吻合。任何人任何时刻都可以用这两个原始数对账。

工程细节:组件与降级行为
  • checkpoint 兼容 NUMA-map 与扁平两种布局;与 Running pod 求交集过滤已终止残留;
  • 能耗计数器回绕钳制为零;抄表失败跳过本轮,下一轮跨越空窗,能耗不丢;
  • 模型名解析:vLLM 指标 model_name 标签 → pod 标签(aitra-ai.github.io/model-name/model/app)→ pod 名;
  • 端点不可达(加载中/非 vLLM)记零产量但能耗照记——占卡即付费;
  • 多进程共享一张卡(MPS)硬件不可拆分 → 退化为按 token 比例分摊并打 attribution_method: proportional 标签;不测 prefill/decode 分相能耗(口径红线);
  • 采集器 RBAC 最小化:pods/nodes 只读;runAsUser: 0 仅因 checkpoint 目录 root-only。

跑的是什么(模型、流量与两种状态)

最重要的一条认知:J/token 不是模型的固有属性,是"模型 × 负载"的联合属性。所以下面给每个模型两个数:基线值(并发≈1,保守上界)与满载值(持续压测,生产下界)——差距就是批处理能挖的优化空间。

3.2 四条现成的叙事线

  • 尺寸梯度 — 0.8B→27B,基线单价涨 7.5 倍:越大越费电,现在有实测数字;
  • 量化 A/B — 同一个 Qwen3.6-27B,FP8 比 bf16 省 38%(13.63 vs 8.48),满载态同样保持优势;
  • MoE 稀疏激活 — 35B-A3B 的电费只相当于 2B 稠密档:烧电的不是参数量,是激活量;
  • 批处理红利与模型大小成反比 — 小模型满载降 20 倍,27B 只降 8 倍:小模型单卡算力过剩,可摊的"闲置电"多。这条规律直接指向调度策略(小模型更该拼卡/合批)。

  • 📈 并发扫描 1→32(约 12 分钟)— 对选中模型逐档爬升,Demo C 的下坡曲线一键复现;

  • ■ 全部停止 — 熔断:删掉所有演示任务,一分钟内回到底噪稳态。

4.3 一套可直接照做的演示剧本(约 15 分钟)

  1. 稳态开场 — Grafana Demo A:8 tile 各安其位,讲尺寸梯度与 MoE 反常识行;
  2. 空载 — 控制台关底噪:60 秒内全员归零、功率露出静息底座("不干活也在烧电,这就是 idle 成本");
  3. 恢复 + 单点压测 — 开底噪;选 0.8B,真实对话 × 并发64 × 持续:它的 J/token 从 1.8 俯冲到 0.09("同一张卡,单价差 20 倍");
  4. 对比实验 — 多选 27B + 27B-FP8,同场景同压:两条曲线并排,量化省电肉眼可见;
  5. 心跳收尾 — 全选 8 模型点脉冲,全场曲线同频起伏;讲完点"全部停止",一切归于平静。

安全边界:控制台仅限内网、无登录鉴权,严禁开公网隧道。它的 K8s 权限被 RBAC 钉死:只能创建/删除本命名空间的压测 Job、只能伸缩 loadgen 这一个 Deployment;每个任务都有硬时限与自动清理;同一模型同时最多一个任务、全局最多 8 个。

Prometheus 是数字仓库:算账器每 15 秒被抓取一次,历史保留 2 天。看板上的一切都是从它查出来画的;会 PromQL 的人可以直接问仓库。
指标记的是什么
aitra_j_per_token头号账本:每模型当前单字电费(遵循 §2.2 的显示语义:可信值或 0)

6.5 红灯清单(看到就停)

两块数字牌长期一模一样 → 归因泄漏,切录播排查。

TP=1 读出整机级电费 → 闲卡漏进分子,分组坏了。

CV 长期 > 3% → 数字不可引用,先查流量是否断续。

产字归零但功率仍在 → 服务活着没流量,查底噪开关/任务列表。

故障降级阶梯:远程全量 → 单模型整机 → 备用 GPU 服务器本地 → 录播。命令见 docs/demo/kubecon-runbook.md。

问答
Aitra Meter 是什么?解决什么问题?一个开源的 AI 推理能耗计量器(Prometheus exporter 形态):在多模型共享 GPU 集群里,把每一焦耳精确记到具体模型头上,输出 J/token(每 token 焦耳)及派生的成本/碳排指标。解决的是"AI 电费只有一张总账单,没人知道哪个模型花的"这个盲区。
和 Kepler / DCGM-exporter / Scaphandre 有什么区别?它们输出硬件或容器维度的功耗;Aitra Meter 在其上补了关键一层:按模型归因 + 与 token 产出对齐——分子(该模型持有的 GPU 的实测能耗)和分母(该模型自己产出的 token)都按模型隔离,得到推理领域真正可比的效率单位。事实上我们把 DCGM 当数据源,与 Kepler 的集成在路线图上(issue #48)。
为什么选 J/token 这个单位?它是推理能效的"每公里油耗":跨模型、跨硬件、跨负载可比,直接乘电价/碳强度就是钱和碳。我们同时在推动 OTel GenAI 语义约定收录 gen_ai.infrastructure.energy.*(issue #38),希望它成为行业通用口径。
项目状态和许可?Apache-2.0,仓库 github.com/aitra-ai/aitra-meter,当前 v0.8 线,Helm 一键部署。欢迎 issue/PR——展台演示跑的就是主干代码。

技术原理

问答
能耗怎么归因到单个模型?三步:①从 kubelet device-plugin checkpoint 读"哪个 pod 持有哪几张 GPU"(K8s 本来就记录,零配置);②从 DCGM 读每张 GPU 的硬件累计能耗计数器做窗口差分;③"卡按持有 pod 分组、求和只在组内"——单卡模型是精确测量,TP 多卡模型恰好求和参与卡,空闲卡单独记 idle,永不摊派。
需要改我的模型或推理代码吗?零侵入。agent 自动发现持卡 pod、抓引擎自带的 /metrics(vLLM 的 token 计数器);模型上线自动出现、下线自动消失。展台上平台方部署的第三方模型就是被自动发现计量的。
精度如何?是测量还是估算?整卡独占场景是测量(硬件计数器,非模型化估算):同一模型隔离运行 vs 8 模型共驻,J/token 偏差约 1%。每个数字配有 CV(变异系数)稳定门,<3% 才标记可信;不足 30 token 的窗口一律不出数——非零即可信。
J/token 是模型的固定属性吗?不是——它是模型 × 负载的联合属性。同一模型并发 1 和并发 64 能差 20 倍(批处理摊薄固定功耗)。所以我们总是带负载上下文给数字:基线值是容量规划上界,满载值是生产下界,差距就是优化空间。
测量开销多大?接近零:纯 scrape 模式(读 DCGM 与引擎已有的 /metrics),无 eBPF、无插桩、无采样进程;agent 是每节点一个 <100MB 的 Go 进程,CPU 毫核级。
支持哪些推理引擎和硬件?引擎:vLLM 原生;SGLang/Triton/Ollama 适配在评审中(PR #69/#88),另有 generic-prometheus 适配器接任意暴露 token 计数的引擎。硬件:NVIDIA(DCGM/NVML)为主,AMD provider 已有;MIG 切片计量在 PR #71。
多卡张量并行怎么算?共享 GPU 呢?TP=k 的 pod 持有 k 张卡 → 恰好这 k 张求和,TP=1 时其余 7 张卡的空转不会漏进分子(展台 Demo B 专门验证这点)。多进程挤同一张卡(MPS/分时)硬件计数器无法拆分——退化为按 token 比例分摊并打 attribution_method: proportional 标签,诚实降级而不是假装精确。
能区分 prefill 和 decode 的能耗吗?不能,这是明确的 non-goal——硬件计数器没有相位概念,任何声称按相位拆分能耗的都是模型估算而非测量。我们展示的是"负载形态影响聚合 J/token"(读重/写重形态差异),口径严格。
只算 GPU 电吗?CPU/整机呢?当前 J/token 是 GPU-only(推理能耗大头),文档明确标注。主机侧能耗(RAPL/机箱)在 PR #84,落地后会提供 GPU+host 的全口径指标。

落地与生态

问答
部署需要什么?多快能跑起来?任何有 NVIDIA device plugin 的 K8s 集群 + dcgm-exporter;Helm 一条命令装 agent(DaemonSet)+ 聚合服务 + Grafana 仪表盘。展台这套 8 模型环境从零到出数不到一天,单集群试用半小时内见到第一条 J/token。
怎么变成钱和碳?能接计费吗?按站点参数(PUE、电价、电网碳强度)从 J/token 透明换算 —— 每个数字的推导公式直接印在看板上;自带 namespace 维度 30 天 chargeback 聚合与 CSV 导出,可直接喂内部分摊/账单系统。
数据能进我现有的监控栈吗?天然可以:一切都是标准 Prometheus 指标(aitra_* 系列),Grafana/Alertmanager/Thanos 照常用;另有 OTLP 导出器把窗口数据推给 OpenTelemetry Collector。
展台看到的数据是真的吗?全部实测实时:身后就是 8×A100 服务器,8 个 Qwen3.5/3.6 模型在跑,你现在扫码打开 meter.aitra.ai 看到的就是它们此刻的功耗——欢迎用控制台亲手改负载,看曲线 10 秒内响应。
路线图上有什么?近期:SGLang/Triton/Ollama 引擎适配、MIG 切片计量、主机侧能耗、Kepler 集成;中期:OTel GenAI 能耗语义约定、llm-d/KAI 等调度生态的能效信号。欢迎在 issues 认领。
